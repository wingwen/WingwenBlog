# 技术决策记录

> 每条记录：为什么这样选、放弃了什么、什么情况下应该重新考虑。
> 这份文件是对外公开的版本；`.trellis/tasks/` 下的 `design.md` 是更详细的工作副本。

---

## D1 · 为什么用静态站点

**决定**：整站构建为静态 HTML，不使用服务端渲染。

**理由**：站点内容全部是项目说明与个人资料，没有登录、没有个性化、没有实时数据。构建期就能确定所有页面内容，运行时不需要服务器。

**换来什么**：加载快、零运维成本、免费托管、迁移只需重传一个目录。

**放弃了什么**：需要运行时数据的页面（如实时评论、搜索建议）做不了；改内容需要重新构建。

**何时重新考虑**：如果将来要加评论或在线编辑器，届时再引入后端——而不是现在为可能性付费。

## D2 · 为什么不直接套用博客主题

**决定**：从最小模板开始，自己实现布局与样式。

**理由**：套用完整主题会导致两个问题：一是样式体系庞大，改一个细节要摸清别人的抽象；二是视觉方向 A 依赖精确的排版控制，与通用主题的卡片式布局冲突。

**参考边界**：可以借鉴 Firefly 等开源作品的**设计思路**（信息组织方式、留白节奏），但不复制代码与整站结构。所有参考来源与许可证记录在 `docs/credits.md`。

**代价**：需要手写样式，比套主题慢。这是有意接受的成本。

---

## D3 · 为什么不用 Tailwind，改用手写 CSS

**决定**：手写 CSS + CSS 自定义属性，分层为 tokens / base / layout / components。

**理由**：方向 A 的核心是排版细节——行高、行长、基线节奏、编号对齐。这些用工具类反而更难精确表达。同时 CSS 变量与设计 token 一一对应，改一处颜色只改一个变量。

**放弃了什么**：Tailwind 在快速搭通用界面上更快，社区示例更多。

**何时重新考虑**：如果项目转向大量重复的管理型界面（本项目不会）。

---

## D4 · 为什么中文不加载 web font

**决定**：拉丁文用可变字重 webfont，中文走系统字体栈（宋体 / 苹方等）。

**理由**：一个完整的中文字体文件通常有数 MB，会让首屏加载从 100ms 级变成数秒，与"静态站点加载快"的核心优势直接冲突。系统字体在 macOS / iOS / Android 上都有合格的serif 与 sans-serif。

**代价**：不同系统下中文观感有细微差异。

**何时重新考虑**：如果将来确需统一中文观感，可考虑按需子集化的中文字体，并接受额外的加载成本。

## D5 · 为什么 AI 助手单独隔离成一个服务端函数

**决定**：主站保持纯静态，AI 能力放在平台提供的服务端函数目录中，与主站构建完全分离。

**理由**：
1. 大模型 API Key 不能出现在前端，否则等于公开。
2. AI 是唯一需要运行时的部分，隔离后它出故障不会导致主站白屏。
3. 不引入 Astro 的 SSR 适配器，整站部署复杂度不变。

**放弃了什么**：换部署平台时，这个函数需要按新平台的格式重写一份。这部分"可迁移性"是牺牲掉的。

**何时重新考虑**：如果 AI 功能成为站点核心（本项目不是），就该考虑正经的 BFF 层。

## D6 · 为什么检索用关键词打分，而不是向量检索

**决定**：构建期生成片段索引，运行时用关键词/二元字组打分取前 N 段，再交给模型回答。

**理由**：站内内容总量在几十个片段量级，向量检索带来的召回提升不足以抵消引入嵌入模型、向量存储与额外 API 调用的成本。关键词方案完全透明、可单元测试、可解释阈值。

**关键设计**：最高分低于阈值时**不调用模型**，直接回答"站内没有相关内容"。这既省钱，也从源头减少编造。

**何时重新考虑**：内容规模上升导致召回明显不足时（例如上百条项目与资料片段）。

## D7 · 为什么测试只覆盖少数几处

**决定**：只测项目排序与格式化纯函数、AI 检索打分与阈值、内容 schema 校验。不引入 E2E 框架。

**理由**：测试的价值来自"这类错误真的会发生，且不测就会漏"。页面渲染的回归在本周期属于人工验收能覆盖的范围；E2E 的搭建与维护成本高于它可能发现的问题。

**明确立场**：不写为覆盖率而写的测试，也不用测试数量充数。

> 2026-11-01 更新：原定的"标签筛选纯函数"随文章栏目移除而消失，那批 15 条测试一并删除，仓库一度**没有单元测试**。
> 现在补的是 `lib/projects.ts` 的 8 条测试，理由是它被首页、项目列表、详情页三处共用，排错一次整站都错——这正是当年真实发生过的回归（三个 2026 年项目退化成按文件名排）。

**何时重新考虑**：站点出现反复被同一类改动弄坏的页面时，再针对性补 E2E。

## D8 · 为什么 `.trellis/` 和 `.cursor/` 不进 Git

**决定**：两者在 `.gitignore` 中整体忽略，对外过程记录统一整理到 `docs/`。

**理由**：这两个目录混合了个人身份信息、会话日志、运行时状态与约 80 个工具配置文件。逐条挑选白名单容易遗漏，一旦漏了就会把私人记录公开。整体忽略 + `docs/` 重新整理，是更安全的做法。

**代价**：Trellis 的 spec 与任务历史不随仓库共享。对个人项目可接受。

**何时重新考虑**：如果有合作者需要共享工程规范时，再把 `.trellis/spec/` 单独纳入。
